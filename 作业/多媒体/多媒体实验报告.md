### \[1-2\]
根据 Microsoft Learn 的官方文档，mciSendCommand() 和 mciSendString() 都是用于控制多媒体设备（如播放音频、视频等）的函数，但它们提供了两种截然不同的接口方式。

核心差异在于：**mciSendCommand 是基于“消息和结构体”的接口，而 mciSendString 是基于“文本字符串”的接口。

以下是对比分析：
#### 1. 接口形式 (Interface)
- **mciSendCommand()**:
    - **类型**：**命令消息接口 (Command-Message Interface)**。
    - **工作方式**：你需要传递**常量**（如 MCI_OPEN, MCI_PLAY）和**数据结构**（如 MCI_OPEN_PARMS）给函数。
    - **参数**：需要指定设备 ID (MCIDEVICEID)、消息常量、标志位 (Flags) 以及指向包含参数的结构的指针。
- **mciSendString()**:
    - **类型**：**命令字符串接口 (Command-String Interface)**。
    - **工作方式**：你传递由人类可读的**英文指令字符串**（如 "play mymusic.wav" 或 "open cdaudio"）。
    - **参数**：主要是一个以 null 结尾的命令字符串。
#### 2. 信息获取与返回值 (Information Retrieval)

**mciSendCommand()** 数据会直接填充到输入的的**结构体**成员中；**mciSendString()**:
数据会以**文本字符串**的形式返回到缓冲区中。

| 特性               | mciSendCommand()        | mciSendString()      |
| ---------------- | ----------------------- | -------------------- |
| **接口类型**         | 消息与结构体 (Binary/Structs) | 文本字符串 (Text Strings) |
| **参数传递**         | 指向结构体的指针                | 英文句子 (如 "play ...")  |
| **数据返回**         | 直接写入结构体字段 (int/bool等)   | 返回字符串 (需解析，如 "true") |
| **易用性**          | 较难 (需了解具体结构体)           | 简单 (像写脚本指令)          |
| **灵活性**          | 高 (适合复杂的程序逻辑控制)         | 中 (适合快速实现功能)         |
| **Microsoft 建议** | 适合 C 应用程序，因为结构体易于解释     | 适合不使用返回值的简单操作        |

### \[1-4\]
录制分为五步：打开，录制，停止，保存，关闭

**mciSendString :**
```c++
#include <Windows.h>
#include <iostream>
#include <conio.h> // 用于 _getch()

#pragma comment(lib, "winmm.lib")

int main() {
    std::cout << "=== MCI 录音测试 (mciSendString) ===" << std::endl;

    // 1. 打开设备
    // "new type waveaudio" 表示创建一个新的波形音频
    // "alias myMic" 给它起个名字叫 myMic，后面都用这个名字操作
    MCIERROR err = mciSendString(TEXT("open new type waveaudio alias myMic"), NULL, 0, NULL);
    if (err) {
        std::cout << "打开录音设备失败！" << std::endl;
        return 1;
    }

    // (可选) 设置音频质量。默认质量很低(8bit/11kHz)。
    // 这里设置为 CD 音质 (16-bit, 44100Hz, Stereo, PCM)
    // 注意：bytespersec = samplespersec * channels * (bitpersample / 8)
    mciSendString(TEXT("set myMic time format ms bitpersample 16 channels 2 samplespersec 44100 bytespersec 176400 alignment 4"), NULL, 0, NULL);

    // 2. 开始录制
    std::cout << "正在录音... (按任意键停止)" << std::endl;
    mciSendString(TEXT("record myMic"), NULL, 0, NULL);

    // 等待用户按键
    _getch();

    // 3. 停止录制
    mciSendString(TEXT("stop myMic"), NULL, 0, NULL);

    // 4. 保存文件
    // 注意：路径建议使用绝对路径，或者确保程序有写入当前目录的权限
    std::cout << "正在保存到 result.wav ..." << std::endl;
    mciSendString(TEXT("save myMic \"result.wav\""), NULL, 0, NULL);

    // 5. 关闭设备
    mciSendString(TEXT("close myMic"), NULL, 0, NULL);

    std::cout << "完成！请检查程序目录下的 result.wav" << std::endl;
    return 0;
}
```

**mciSendCommand :**
```c++
#include <Windows.h>
#include <iostream>
#include <conio.h>

#pragma comment(lib, "winmm.lib")

int main() {
    std::cout << "=== MCI 录音测试 (mciSendCommand) ===" << std::endl;

    MCIERROR err;
    MCIDEVICEID deviceID;

    // 1. 打开设备 (Open)
    MCI_OPEN_PARMS openParams = {0};
    openParams.lpstrDeviceType = TEXT("waveaudio"); // 指定类型
    openParams.lpstrElementName = TEXT(""); // 空字符串表示 new

    // MCI_OPEN_ELEMENT 标志在这里表示我们不打开现有文件，而是通过 type 打开
    err = mciSendCommand(0, MCI_OPEN, MCI_OPEN_TYPE | MCI_OPEN_ELEMENT, (DWORD_PTR)&openParams);
    if (err) {
        std::cout << "打开设备失败，错误代码: " << err << std::endl;
        return 1;
    }
    
    deviceID = openParams.wDeviceID; // 获取分配的设备 ID

    // 2. 开始录制 (Record)
    MCI_RECORD_PARMS recordParams = {0};
    std::cout << "正在录音... (按任意键停止)" << std::endl;
    
    // 不加 MCI_WAIT，否则会一直卡在录音函数里直到填满内存
    err = mciSendCommand(deviceID, MCI_RECORD, 0, (DWORD_PTR)&recordParams);
    
    // 等待用户按键
    _getch();

    // 3. 停止录制 (Stop)
    // 实际上 MCI_STOP 不需要参数结构，但通用做法传 Generic 结构或 NULL
    mciSendCommand(deviceID, MCI_STOP, 0, 0);

    // 4. 保存文件 (Save)
    MCI_SAVE_PARMS saveParams = {0};
    saveParams.lpstrFileName = TEXT("command_result.wav");
    
    std::cout << "正在保存..." << std::endl;
    // 使用 MCI_WAIT 确保文件保存完再继续执行下面的 Close
    err = mciSendCommand(deviceID, MCI_SAVE, MCI_SAVE_FILE | MCI_WAIT, (DWORD_PTR)&saveParams);
    
    if (err) {
        std::cout << "保存失败！" << std::endl;
    }

    // 5. 关闭设备 (Close)
    mciSendCommand(deviceID, MCI_CLOSE, 0, 0);

    std::cout << "完成。" << std::endl;

    return 0;
}
```

### 思考题1
#### 1. 什么是 MCI 接口
**MCI (Media Control Interface，媒体控制接口)** 是 Windows 操作系统提供的一套**高层**、与**设备无关**的多媒体 API。它为应用程序提供了一种标准化的方式来控制各种多媒体设备（如声卡、CD光驱、MIDI 合成器、视频播放设备等）。程序员不需要了解底层硬件的具体指令（例如不需要知道怎么操作特定型号的声卡寄存器），只需要发送通用的 MCI 命令（如 "Open", "Play", "Stop"），MCI 驱动程序会将这些命令翻译成特定硬件能理解的操作。

#### 2. MCI 所囊括的内容
MCI 的体系结构主要包含以下三个方面：
- **两种编程接口（调用方式）：**
    1. **命令字符串接口 (mciSendString)**：允许应用程序通过发送人类可读的英文文本字符串（如 "play music.wav"）来控制设备。这种方式简单直观，适合脚本语言或快速开发。
    2. **命令消息接口 (mciSendCommand)**：使用常量消息（如 MCI_PLAY）和数据结构（如 MCI_PLAY_PARMS）进行控制。这种方式更适合 C/C++ 开发，具有更强的类型检查和参数控制能力。
- **设备类型 (Device Types)：**  
    MCI 定义了一系列标准设备类型，囊括了多种媒体形式，主要包括：waveaudio ，sequencer ，cdaudio， digitalvideo / avivideo， overlay。
- **命令集 (Command Sets)：**  
    MCI 定义了一套标准命令，分为四类：
    1. **系统命令**：直接由 MCI 系统处理，不涉及具体设备（如 sysinfo）。
    2. **必需命令**：所有 MCI 设备都必须支持的命令（如 open, close, capability, status）。
    3. **基本命令**：多媒体设备常用的命令（如 play, stop, pause, resume, record, save, seek）。
    4. **扩展命令**：特定类型设备特有的命令（如 CD 的 eject，视频的 window）。

### 思考题2
在 Windows 编程中，播放 WAV（波形）文件主要有以下几种常用方法：
#### 1. 使用 PlaySound() 函数
这是最高层、最简单的 API
- **优点**：
    - **极其简单**：通常只需一行代码。
    - **资源支持**：可以直接播放通过资源文件嵌入到 EXE 中的音频，无需外部文件。
    - **便捷**：适合播放系统提示音、简单的按键音效。
- **缺点**：
    - **控制力弱**：无法控制音量、无法跳转进度（Seek）、无法获取播放进度。
    - **单音轨**：同一时间只能播放一个声音（除非极其复杂的设置），新声音会打断旧声音。
    - **加载限制**：对于大文件，它通常会尝试将其全部载入内存，可能导致程序卡顿。
#### 2. 使用 MCI 接口 (mciSendString / mciSendCommand
基于 MCI 的 waveaudio 设备类型。
- **优点**：
    - **功能全面**：支持播放、暂停、继续、停止、跳转（Seek）、录音、保存。
    - **格式兼容**：除了 WAV，还能处理 MIDI 和 MP3（通过系统编解码器）。
    - **易用性**：比底层 API 简单，比 PlaySound 灵活。
- **缺点**：
    - **延迟**：由于经过了高层封装，启动播放可能有轻微延迟，不适合对实时性要求极高的动作游戏。
    - **过时技术**：微软已将其标记为 Legacy，现代开发中逐渐被新技术取代。

#### 3. 使用低级音频 API (WaveOut 系列函数)
使用 waveOutOpen, waveOutWrite, waveOutClose 等函数。
- **优点**：
    - **精准控制**：允许直接操作音频缓冲区（Buffer），可以动态生成音频数据。
    - **兼容性好**：向后兼容性极强，几乎支持所有版本的 Windows。
- **缺点**：
    - **开发极难**：需要手动管理内存块、双缓冲机制、回调函数、线程同步等，代码量巨大且容易出错。
#### 4. 使用 DirectSound / XAudio2 (DirectX)
这是游戏开发中的标准选择。
- **优点**：
    - **低延迟**：反应速度极快，适合游戏音效。
    - **混音能力**：可以同时播放多个声音（背景音乐+爆炸声+语音），硬件会自动混音。
    - **3D 音效**：支持空间音效处理（如声音随距离衰减、多普勒效应）。
- **缺点**：
    - **环境依赖**：需要 DirectX SDK 支持。

    - **学习曲线**：比 PlaySound 复杂得多，需要理解 COM 接口和音频图（Audio Graph）概念。


## 实验二：WAVE文件格式分析
#### \[2-5\] WAVE 文件保存有哪些信息，以什么格式存储？
- **保存的信息**:
    1. **格式信息**: 采样率 (如 44100Hz)、声道数 (单/立体声)、量化精度 (如 16位)、数据传输速率。
    2. **数据长度**: 音频数据的总字节数。
    3. **波形数据**: 实际的声音样本数据 (PCM 脉冲编码调制)。
- **存储格式**:
    - 采用 **RIFF (Resource Interchange File Format)** 格式。
    - 数据以 **Chunk (块)** 的形式组织。最基本的结构包括 RIFF 头，fmt 块 (格式) 和 data 块 (数据)。
#### \[2-6\] 在同一个程序中能不能同时进行播放和录制两项操作？为什么？这对声卡有什么要求？
- **能不能**: 能
- **为什么**: 现代操作系统（如 Windows）和驱动程序支持多线程和并发 I/O，允许同时打开输入流 (waveIn) 和输出流 (waveOut)。
- **对声卡的要求**: 声卡硬件必须支持 **全双工 (Full Duplex)** 模式。
    - 半双工 (Half Duplex): 同一时间只能录或放。
    - 全双工: 可以同时录和放（绝大多数现代声卡都支持）。

#### \[2-7\] 资源交换文件格式（RIFF）有什么特点？
1. **块 (Chunk) 结构**: 所有数据都存储在块中，每个块包含 ID (4字节) 和 Size (4字节)。
2. **嵌套/层级性**: RIFF 块可以包含子块（如 WAVE 文件本身就是一个大的 RIFF 块，里面包含 fmt 和 data 子块）。
3. **可扩展性**: 如果程序遇到不认识的块 ID，可以根据块的大小直接跳过，不影响读取其他标准块。这使得在不破坏兼容性的情况下添加新元数据（如版权信息、歌词）成为可能。

### T2
量化的表达式为$$F^Q(u,v)=\frac{F(u,v)\times 8}{g_{scale}\times Q(u,v)}$$

#### 增大 g_scale 或 矩阵元素
- **压缩比 (Compression Ratio)**：**变高**（文件变小）。
    - **原理**：DCT 系数除以更大的数，结果会变得更小。许多原本较小的的高频系数会被量化为 **0**。
    - **结果**：在后续的 Zigzag 扫描和行程编码（RLE）中，会出现更长的“连续 0”，哈夫曼编码能极其高效地压缩这些数据。
- **图像质量 (Image Quality)**：**变差**。
    - **现象**：
        - **块效应 (Blocking Artifacts)**：8x8 的方块边界变得明显。
        - **细节丢失**：图像的纹理、边缘变得模糊。
        - **振铃效应 (Ringing)**：在强边缘附近出现“鬼影”或波纹。

#### 减小 g_scale 或 矩阵元素
- **压缩比 (Compression Ratio)**：**变低**（文件变大）。
    - **原理**：除数变小，商保留了更多的数值精度，非零系数的数量增加。
    - **结果**：编码所需的比特数大幅增加。
- **图像质量 (Image Quality)**：**变好**。
    - **现象**：重建图像更接近原始图像，细节保留完整，几乎看不出压缩痕迹。

#### 修改矩阵中不同位置的元素
[Q_MATRIX](vscode-file://vscode-app/d:/Program%20Files%20\(x86\)/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 是一个 8x8 的矩阵，对应 DCT 变换后的频率分量：

- **左上角 (低频/DC)**：代表图像的平均亮度和主要色调。
    - **影响**：如果增大这里的量化值，图像会出现严重的色块，视觉质量下降极其明显。通常这里的值设得很小（如 16, 11, 10）。
- **右下角 (高频/AC)**：代表图像的快速变化细节（噪点、锐利边缘）。
    - **影响**：人眼对高频细节不敏感。增大这里的量化值（如 99, 100），虽然丢失了细节，但人眼很难察觉。这是 JPEG 高压缩比的主要来源。

### T3
#### 数据范围
输入数据为原始像素，即8位无符号整数[0,255]，**平移**后，范围变为[-128,128]。

进行**DCT变化**后，DCT 变换本质上是一种加权求和。而DC 系数大致相当于 8×8 像素块的总和（取决于归一化因子的具体实现，标准 JPEG 中通常放大 8 倍）。故范围为 [−1024,1023]。

执行**量化操作**后，由于量化是除法操作$F^Q(u,v)=Round(F(u,v)/Q(u,v))$。因为 Q(u,v)≥1Q(u,v)≥1，量化后的数值绝对值只会变小或不变，故范围依然在 [−1024,1023] 范围内，但通常会小得多。

#### 是否有可能超出范围
使用默认量化表，则AC系数对应的量化值较大，不会超出范围。如果将量化表全部设为1，则某些特殊的点可能产生接近1024高频系数，此时可能会超出范围
